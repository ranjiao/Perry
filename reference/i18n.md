# Languages

## Two settings

Document language controls newly authored file prose (default English). Chat
language controls conversation (default follow user). Read skill preferences
through `config.md`; do not hand-edit frozen configuration JSONL. Changing the
setting does not retroactively translate existing documents.

## Invariants

Never translate IDs, native command/field/state/enum names, paths, slugs, URLs,
contract keys, actor identities or exact quotations. Native data remains the same
while the agent renders readable titles, explanations and questions. Preserve
reference targets and actual source wording. English templates are source
scaffolds: translate narrative guidance at authoring time, not kernel JSON keys.
There is no legacy localization schema or markdown parser to satisfy.

## Writing chat prose in a language that is not English

Keep technical terms without a settled equivalent in English. Translate an
idiom's meaning, not its literal words. Use the target language's sentence
structure; lead with the user's decision or result. If wording is unclear,
rewrite that explanation plainly without changing technical facts or evidence.

## Switching language mid-project

State the scope of the requested change. Preserve historical evidence and exact
quotes. Do not translate records or IDs to create a second current-state store.
A request to translate existing documents identifies the finite files and their
owners first, then preserves headings/references needed by readers. Review every
changed link, decision and technical qualification after translation.

## Checklist before a write

Check document/chat preferences, invariant identifiers, source quotes, internal
links, ownership and the semantic rubric in `operating-rules.md`. Native query
errors are rendered faithfully, never softened into success. A prose translation
cannot itself validate code behavior or a kernel contract.
