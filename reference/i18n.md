# Localization — what Perry writes in which language

> Read this before writing any state file, rendering any dashboard, or adding
> a language. It is the shared contract for all three lanes (`okr`, `pmo`,
> `design`), the two orchestrators (`adopt`, `diagnose`), the deterministic
> scripts under `bin/`, and any external reader of Perry's files.

Perry was designed and written in English. That is a fact about its source, not
a constraint on its users: a project's goals, decisions and design docs are
long-lived documents that the *user* reads months later, and a document nobody
enjoys reading is a document nobody re-reads. So the language a project's files
are written in is a per-project setting, and the language Perry talks in is a
separate one.

## Two settings, deliberately separate

Both live in `.perry/config.md`, written once at first-time setup and readable
by every lane on every invocation.

| Field | Governs | Default | Changing it |
|---|---|---|---|
| `Document language` | Everything **written to a file**: OKR prose, phase narrative, BOARD titles and next-actions, journal entries, ADR reasoning, design docs, weekly reports, handoffs, evidence, delegation prompts. | English | Applies to newly written content. Perry does **not** retro-translate existing files — see § Switching language. |
| `Chat language` | Everything **said in the conversation**: the standup dashboard, TL;DR lines, suggested next actions, `AskUserQuestion` labels and descriptions, warnings, confirmations. | `follow user` — mirror whatever language the user just typed | Takes effect immediately, from the next reply. |

They are separate because the common case wants them apart. A user who thinks
in Chinese but works on an English-language open-source project wants
`Document language: English` (the files are shared) and `Chat language: 中文`
(the conversation is theirs). The reverse is just as common: an internal
project where the docs are Chinese but the user is happy reading English
status lines.

`Chat language: follow user` is the default because it is almost always right
and it costs the user no decision. Pin it to a named language only when the
user asks — for instance because they type English commands out of habit but
want to read Chinese.

**One rule that overrides both:** never translate a quoted artifact. If a
command, a file path, an error message, a commit subject, or a user's own
sentence is being echoed back, it is reproduced verbatim.

## The three layers of text

Everything in a Perry state file falls into exactly one of these. Getting a
token into the wrong layer is how a project stops being machine-readable.

### 1. Invariant — never translated, in any language

These are matched, joined, or dereferenced by code. They stay ASCII/English
even in a fully Chinese project. The authoritative list is
`schema/state-schema.json § i18n.invariant`; in summary:

- **File and directory names** — `BOARD.md`, `phase/`, `evidence/2026-08/`,
  `decisions/ADR-001-<slug>.md`.
- **Slugs** — the `<slug>` in `phase/001-release-pipeline.md` and
  `design/DESIGN-002-flake-scoring.md`. A Chinese phase file is titled
  `# 阶段 #001 — release-pipeline`: the heading is localized, the file name is
  not. Slugs are typed at a shell, completed by a tab, and pasted into git
  branch names — ASCII is a kindness, not an oversight.
- **IDs**, prefix and body — `REL-002`, `ADR-001`, `DESIGN-001`, `KR-O1.2`,
  `P<NNN>-O<n>-KR<n>`, `USER-014`, `CAD-001`.
- **Enum values** — `not_started`, `in_progress`, `blocked`, `review`, `done`,
  `dropped`, `draft`, `locked`, `single`, `split`, and the owner vocabulary
  (`Coding Agent`, `PMO Agent`, …). A status cell reads `blocked`, with any
  qualifier in the document language: `blocked (等 USER-014)`.
- **Priority sections and section markers** — `## P0`, `## P1`, `## P2`,
  `## §1 … §8` in `ARCHITECTURE.md`.
- **`.perry/config.md` field names** — this is the file that *declares* the
  language, so it must be readable before the language is known.
- **YAML frontmatter** in `phase/<NNN>-linkage.md` — keys and values both. It
  is machine-written and machine-read on both sides.
- **Dates** (`YYYY-MM-DD`), ISO weeks (`YYYY-WW`), commit SHAs, paths.
- **Command names** — `/perry okr plan-phase`, `bin/perry-lint`.

### 2. Localizable structure — translated via the glossary

Section headings, table column headers, and the three localizable header
fields (`Started`, `Status`, `Date`). These are structure the *user* reads, so
they follow the document language — but a reader still has to find them, which
is why the accepted spellings are declared rather than invented per project.

The glossary is `schema/state-schema.json § i18n` (`headings`, `fields`,
`columns`). Every reader resolves through it:

| Reader | How |
|---|---|
| `bin/perry-lint` | `COLUMN_ALIASES` / `FIELD_ALIASES`, loaded from the schema in `main()`; headings via the widened `match` regexes in `files[].headings` |
| `viewer/parsers.py` | `alias()` / `heading_is()` / `_column_keys()`, loaded lazily from the same schema |
| `bin/perry-state` | via `viewer/parsers.py` |
| external frontends (aiMark) | their own parser, written to the same schema block |

**Use the glossary spelling, not a synonym.** `## 主要风险` is the declared
Chinese form of `## Top risks`; `## 主要风险点` is not, and the risk panel will
be empty with nothing to explain why. When a heading you need has no glossary
entry, add one (see § Adding a language) rather than improvising.

### 3. Prose — always the document language

Titles, descriptions, next actions, mission statements, KR text, rationale,
retro notes, ADR Context/Options/Chosen/Consequences, design narrative,
delegation instructions. All of it, end to end. **No mid-file switching** — a
document written half in each language is worse than either, because the reader
can no longer skim it.

## Worked example

The same BOARD row in both languages. Note what moved and what didn't:

```markdown
## P0 (must finish this period)

| ID | Title | Owner | Status | Next action | Evidence |
|---|---|---|---|---|---|
| REL-002 | Flake detector | Coding Agent | blocked | waiting on USER-014 | evidence/2026-08/REL-002-spec.md |
```

```markdown
## P0（本周期必须完成）

| 编号 | 标题 | 负责人 | 状态 | 下一步 | 证据 |
|---|---|---|---|---|---|
| REL-002 | 抖动检测器 | Coding Agent | blocked | 等 USER-014 | evidence/2026-08/REL-002-spec.md |
```

`P0`, `REL-002`, `USER-014`, `Coding Agent`, `blocked`, and the evidence path
are byte-identical. The parenthetical after `## P0`, the column headers, the
title and the next action are Chinese. `bin/perry-state` returns the same
payload shape for both — this is exercised by
`tests/fixtures/sample-project-zh/`.

## Templates are English source

`*/state/*_TEMPLATE.md` ship in English and stay that way. There is exactly one
copy of each, and `bin/perry-lint --templates` is the drift guard that keeps it
matching the schema; a parallel Chinese template set would be a second thing to
keep in sync and the first thing to go stale.

When the document language is not English, the writing lane **renders** the
template: it substitutes each heading and column header for its glossary form
and writes the prose in the document language. The structure is unchanged, so
`bin/perry-lint --root .` passes on the result — run it after the first
localized write of any new file type, because that is the cheapest possible
check that the rendering was faithful.

## Scripts speak English; the agent relays

`bin/perry-state`, `bin/perry-lint`, `bin/perry-diagnose`, `bin/perry-explain`
and `bin/perry-update-check` emit English. They are deterministic tools whose
output is also read in CI, in git hooks, and by external frontends; localizing
them would mean localizing a machine interface, and a `--json` payload with
translated keys is a payload nobody can write a stable consumer against.

**The agent translates on relay.** When the chat language is not English and a
script's output is surfaced to the user — a warning, a finding, a lint error —
render it in the chat language and keep the stable parts verbatim: the finding
ID, the file path, the line number, the exact command to re-run. A translated
`LOAD-003` is not findable; the sentence explaining it should be.

The tier-3 consumption surface is **aiMark**, which renders the project's own
content; nothing in this document governs its chrome.

## Writing chat prose in a language that is not English

Everything above governs **files**. This governs **replies** — and it exists
because Perry got it wrong for a whole session while every rule above was being
followed correctly.

The failure is not mistranslation. It is writing an English sentence and
swapping in dictionary words, so the result is Chinese vocabulary carrying
English structure. A user with fifteen years in the industry could not tell what
was being said.

### Rule 1 — a term with no settled equivalent stays English

Mixing is correct. `交付了 contract 2.0` is how the language is actually spoken
in this field; `交付了契约 2.0` is not, because `契约` means a legal covenant and
nobody working on an API says it.

| Invented | What practitioners say |
|---|---|
| 契约 | `contract`，或"接口约定" |
| 载荷 | `payload`，或"接口返回的 JSON" |
| 变异测试 …被抓到了 | "把代码改回错的写法，测试失败了" |
| 杀掉测试 | 同上 |
| 提交了三个 commit | fine — `commit` in English is already the norm |

The test is not "does a Chinese word exist" — one usually does. It is **"would
someone doing this job say it out loud?"** If not, use the English term. This
extends `§ 1 Invariant`: that section keeps English in *files* because code
reads them; this keeps English in *prose* because people read it.

### Rule 2 — translate the meaning, never the idiom

English technical writing is full of figures that do not survive a word swap:
*the mutation was caught*, *the test kills the mutant*, *this smells*, *it
bites you*, *hand-wavy*, *load-bearing*. Rendering them literally produces a
sentence that parses and means nothing.

Say what happened instead. Not "变异被抓到了" but **"我把修好的代码改回原来的
错误写法，跑测试，对应的测试失败了"** — longer, and the only version that
transfers the fact.

### Rule 3 — do not carry English sentence structure

Em-dash appositives, trailing participles, and the "which is X, one lane over"
construction are English rhythm. In Chinese they read as translation artifacts.
Short sentences, one claim each.

### What does not change

`Document language` still governs files, and a file stays in one language end to
end — Rule 1 applies to **chat**, not to `BOARD.md`. IDs, enum values, paths and
commands were already invariant everywhere (`§ 1`), and still are. Nothing here
licenses a half-English board.

### If the user says the writing is unclear

Believe them immediately and ask which term. Do not defend the phrasing, and do
not switch to English wholesale — the fix is the mixed register above, not
abandoning the chat language.

## Switching language mid-project

Changing `Document language` is a **going-forward** change, not a migration.
Perry does not retro-translate, because a machine translation of a locked ADR
is a silent rewrite of a decision record the user is entitled to read exactly
as they wrote it.

When the user asks to switch:

1. Update `.perry/config.md` and say plainly that existing files keep their
   current language.
2. Offer the three honest options for the existing corpus, and let the user
   pick — do not decide this one for them:
   - **Leave it.** Mixed-language history, single-language future. Cheapest,
     and usually right for `journal/`, `evidence/`, and closed phases.
   - **Translate the tier-1 files only** — `OKR.md`, the current phase file,
     `ARCHITECTURE.md`. These are the ones the user actually re-reads. Do it
     as an explicit, reviewed edit per file, never in bulk.
   - **Translate everything.** Say the cost out loud before starting.
3. Log the switch as an ADR (`Type: Process`) so a future session can tell a
   deliberate change from drift.

Whatever is translated must be re-linted (`bin/perry-lint --root .`) before the
session ends — translation is exactly the operation that turns `## Top risks`
into a heading no reader recognizes.

## Adding a language

The mechanism is language-agnostic; the shipped glossary covers `en` and `zh`.

A language with **no glossary block is already supported for prose** — set
`Document language: Français` and every title, description and narrative is
written in French, while headings and column headers stay English. That is a
legitimate, fully working configuration, and it is what Perry does by default
for any language it has not been taught.

To also localize the structure:

1. Add the language code to `schema/state-schema.json § i18n.languages`.
2. Add its spellings under `i18n.headings`, `i18n.fields`, `i18n.columns`.
   Every canonical English key keeps its entry; you are adding, never
   replacing.
3. Widen the `match` regex of each affected entry in `files[].headings` (and
   `files[].tables[].under`) with `|^<localized form>`.
4. Add a fixture project under `tests/fixtures/` in the new language and assert
   it lints clean and produces the same payload shape — copy
   `tests/test_i18n.py`, which exists for exactly this purpose.

Nothing else changes. `bin/perry-lint` and `viewer/parsers.py` read the
glossary at runtime; neither has a language hard-coded.

## Checklist for a lane about to write a file

- [ ] Read `.perry/config.md`. No config and state files already exist → stop
      and run first-time setup rather than guessing the language.
- [ ] Prose in `Document language`, headings and columns via the glossary,
      layer-1 tokens untouched.
- [ ] One language per file, end to end.
- [ ] Quoted artifacts (paths, commands, errors, the user's own words)
      verbatim.
- [ ] Chat reply in `Chat language` (or mirroring the user, when unset) — which
      may differ from what was just written to disk. Say what you wrote; don't
      paste the file back in the other language.
- [ ] `bin/perry-lint --root .` after a structural write.
