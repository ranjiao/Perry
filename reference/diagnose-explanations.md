# Diagnosis reading checklist

These are skill review dimensions, not emitted finding codes or mechanical pass
criteria. Every material finding needs a cited artifact, measurement, mechanism,
uncertainty and concrete outcome. Old finding IDs in historical reports remain
historical references; their automated emissions are proposed retirements.

| Dimension | Read and verify |
|---|---|
| Context | Which instructions actually load? Are empty, duplicate, oversized or dangling rules increasing user/agent effort? Do not infer irrelevance from length. |
| Documents | Can a new reader find current instructions, sources and owners? Distinguish deliberate archives from forgotten live docs. |
| Concurrency | Are worktrees isolated, scope ownership explicit and integration independently reviewed? A recent event does not prove a live executor. |
| Tracking | Can the user state goals, name a runnable check and find the actual decision? Query native items; do not guess intent from Git. |
| User effort | Do IDs carry human titles? Do links resolve? Are open choices consequential and evaluable? A small queue does not prove good decisions. |
| Namespace | Do exact proposed paths collide with existing/foreign files or symlinks? Never claim a conventional directory automatically. |
| Mode fit | Does actual work need project/inquiry/queue/pipeline procedures? Ask before changing method; a classifier is not authority. |
| Process cost | Is the method helping outcomes? Propose the minimum spine, including subtraction, within the user's maintenance tolerance. |

Explain technical phrases with the concrete consequence for this project. Check
actual source content before recommending merges or deletion. Unknown/unreadable
areas are limits in the report, never an empty successful scan.
