# First-time setup

## The procedure

Only a genuinely new project may bootstrap. Run `operating-rules.md` first.
Recovery hazards or interrupted runs stop setup. Existing documents or a missing
store on a migrated project require reconciliation, never an empty replacement.

1. Resolve the absolute project and code roots. Ask for unresolved single/split
   layout, document root, document/chat languages and high-stakes boundaries.
2. Enumerate the exact proposed paths by selected lane. Check every existing
   path and parent for collisions, including symlinks. An unowned nonempty path
   is not available just because its filename looks conventional. Show the
   conflicts and choose a different root; do not claim or overwrite them.
3. Record agreed skill preferences in ordinary `.perry/hook.md` prose through
   the root procedure (`config.md`). Preserve existing policy. Obtain the
   project's high-stakes boundary agreement; an absent/unarmed gate blocks
   automated dispatch until resolved.
4. With bootstrap agreement, run native `init` with the actual actor and agreed
   `state_root`, then `template apply` using the parsed shipped
   `templates/process/perry.json`. Use `describe` for exact JSON and refused
   preconditions. Never hand-edit exports or a database.
5. Load goals, work and decide in turn. Each creates only its owned documents
   and items. Decide owns both `design/` and `decisions/`; work cannot substitute
   for it. No old register, board, current-phase pointer or daily journal is
   created. A kernel relation, not a prose cross-reference, links native items.
6. Query the created items and template, open authored documents, check ownership
   and references, then report what exists and what remains unconfigured.
   Follow `next.md` after successful writes.

No installation, network update, live project migration or human acceptance is
implied by this procedure. For an existing project use the reviewed switch plan
and `version-compatibility.md`.
