# TASK-237 — the reading gate, measured, and it stops the row

**Not a result of TASK-237's work.** The gate its own spec requires before any
deletion, run on 2026-09-14 after TASK-236 closed at V4. The spec says:

> This row must answer the reading question for a BOARD, on its own
> measurement. If the answer is that no command is an adequate reading surface
> for a row's next action, that is a finding and a stop, not a detail to fix
> later.

## 2. The row's own gate is not

`TASK-236-result.md § 3.6` handed this row one thing to measure rather than
assume: *the replacement surface must print a row's `Next action` whole, on the
real maximum.*

| | |
|---|---|
| `perry/BOARD.md` | 154,151 bytes, 99.4% table, 15 columns |
| longest `Next action` in the store | TASK-391, 2,218 bytes |

Every candidate surface, measured on `HEAD`:

| command | prints a row whole? |
|---|---|
| `perry-task list` | **no** — id, priority, status, a truncated title: 4 of 15 columns |
| `perry-task list --json` | carries the text whole, but it is a payload, not a reading surface |
| `perry-explain TASK-391` | **no** — 702 bytes; `next_action`, owner, priority, verification and track absent |
| `perry-tasks render` (no `--write`) | **yes, while the file exists** — stdout byte-identical to `BOARD.md`, 154,151 bytes |
| `perry-tasks render`, `BOARD.md` deleted | **no** — `refused — no BOARD.md at …`, rc 1, 0 bytes |

**The one adequate surface is fed by the file this row deletes.** Delete it and
no command prints a row's next action whole. That is the spec's stop condition,
exactly.

### Why the render cannot run without the file — structural, not a guard

`bin/perry-tasks § render` builds `mod.Board(state_root / "BOARD.md")` and hands
it to `perry_store.render(board, records, mod)`. The task rows are **filled in
place** over the file on disk — its own docstring for `stranded_after_render`
says so: *"The task rows are filled in place, so a deleted row stays deleted and
the record is stranded."* Only `## Intake` is rebuilt from its records.

So the render is a template fill. The board's section order, its header prose
and its fifteen-column layout exist only in the file. A board that renders from
`tasks.jsonl` alone, with no file underneath, is a new renderer — not a check to
remove — and until it exists, deleting the file deletes the only way to read a
row whole.

## 3. A second blocker the spec did not enumerate

Sessions recognise a Perry project by the file:

- `work/SKILL.md:108` — the lane activates when *"a new session opens in a
  project that contains a `BOARD.md` at the root"*;
- `work/SKILL.md:292` — *"If invoked in a project with no `BOARD.md` at the
  project root, ask once"* — the bootstrap trigger.

Delete the file and every new session treats this project as never set up.
`BOARD.md` is named 24 times in `work/reference/subcommands.md`, 13 in
`work/SKILL.md`, 11 in `decide/SKILL.md`, 5 in `goals/SKILL.md` and 4 in
`work/reference/bootstrap.md`.

On a board-less copy, `perry-task list` and `perry-state --json` still exit 0;
`perry-lint` exits 1.

## 4. What this does and does not say

It does **not** say ADR-010 was wrong. It says the order DESIGN-013 § 6 set —
build and prove the render on cheaper files first — was not finished for the
board: the board's render exists and is exact, but it cannot run without the
thing it renders over.

The decision is the user's, in `USER-931`.
