## The staleness clock measures triage, not work

This is the finding of this walk, and it is a measurement defect, not a board problem.

The 2026-09-17 triage recorded **54** rows in its stale table. Today the same thresholds
(P0 ≥3d, P1 ≥7d, P2 ≥14d, measured from `updated`) return **30**. That reads as 29 rows
cleared in three days. It is not.

Of the 29 rows that left the list:

| What actually happened | Rows | Which |
|---|---:|---|
| Closed | 4 | TASK-192, TASK-193, TASK-194 (`done` 2026-09-17), TASK-264 (`done` 2026-09-18) |
| Status changed, still open | 1 | TASK-191 (`not_started → blocked`, 2026-09-18) |
| **Still `not_started`, nothing done** | **24** | every one with `updated = 2026-09-17` |

The histogram is unambiguous — for all 24 still-open rows that left the stale list:

```
updated-date histogram:
   2026-09-17  24
```

The threshold reads `updated`. Triage writes `updated`. **So running triage resets the
clock triage uses to decide what is stale.** Twenty-four rows were de-staled by being
looked at. None of them moved.

The consequence is that "30 stale rows" is not a measurement of backlog depth. It is a
measurement of how many days have passed since somebody last ran triage, and it will
return to roughly this size about seven days after any triage that touches rows.

This is why the count has never converged across walks, and it is why this triage wrote
to no row.

**Filed as a finding, not as a board row**, per the standing rule that findings go in the
evidence. Opening a row for it is a deliberate decision for the user to make.

A candidate fix, recorded so the next reader does not re-derive it: staleness wants a
timestamp that means *when work last moved*, distinct from `updated`, which means *when
the record last changed*. The task store already separates these ideas elsewhere —
`Stage since`, `Arrived` and `Last run` all exist precisely because a derived age needs
its own stored input. Nothing here proposes which field; only that one field is being
asked to carry two meanings.
