## Byte identity — the criterion the whole row rests on

Four combinations through the CLI (`write --from-file` then `diff`), each with
**zero verbatim cells and zero decorated cells**, so nothing was reproduced by
echoing the file back:

- this repo's `perry/OKR.md` — 36 records, identical
- this repo's `.perry/config.md` including its prose section — 7 records, identical
- a copy of `~/proj/gimegime-pmo`'s `OKR.md` — 34 records, identical
- that project's `.perry/config.md` — 6 records, identical

The precedent that made this row dispatchable held: `TASK-037-spec` refuses
automation because *"the risk is not one a test catches"*, and a byte comparison
is exactly the test that catches it.

## The finding beyond the spec, and it is the good kind

The decoration branch of `describe_cell` was an **uncounted fallback**, which
that function's own docstring names as the way a renderer passes `cmp` while
reproducing nothing. Concretely: a hand edit that *appends* to a cell —
`3 of 3 modes live, honest` over a stored `3 of 3 modes live` — keeps the stored
value in place, renders byte-identically, and `diff` calls the file clean. One
whole class of hand edit was invisible to the comparison this row is built on.

The agent added `cells_wearing_decoration` to both reports and made `verify`
fail on it. **Measured 0 across every file in this repository**, so the change is
provably inert today and moved no existing output — it closes a hole rather than
fixing a symptom.

## A deviation the agent made and then corrected against the project's own rule

It first made `perry-goals commit` **refuse** on store drift. That contradicts
Perry's Operating Principle — *"Every write goes through a tool. A hand edit is
reported, never refused"* — and broke a shipped test about ids never being
reused after a hand deletion. Corrected to report on stderr and proceed; the
refusal now lives only in `perry-okr write --from-file`, mirroring
`perry-tasks`. The byte-identity check in the writer stays a refusal, correctly,
because that is a renderer bug rather than a user edit.

Recorded because the correction is the interesting part: the rule that caught it
is written down in this project, and a shipped test enforced it.

## The tension it surfaced rather than resolved — for the user

`SKILL.md` promises `.perry/config.md` is *"a tier-1 file the user owns and edits
directly, because a track is configuration rather than state"*. Making it a
projection turns a hand edit into reported drift. The agent implemented it and
left the decision open: **no store exists until `perry-config write --from-file`
is run, and every read path is unchanged until it is.** So the capability ships
without the promise being broken until someone chooses to break it.

The gate circularity predicted in the brief did bite: `perry-conform § gate_mode`
reads `.perry/config.md` to decide whether writes to it are gated, so a fixture
writing that file is writing the file the gate consults about itself. Benign in
practice — the mode is read from disk before the write, as for every other file —
handled with `GATE_OFF` and documented in two places.
