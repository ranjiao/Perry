### 1b · `perry-task` and `perry-state` disagree about a track's stages — **not fixed**

### 3c · The rest of the rubric

### 3d · The open question the rubric asks the reviewer to answer

**Four columns — `ID | Risk | Opened | Status` — is the right set. Keep it.**

Argued from what a reader of this section needs: *which risk, is it still live,
how long has it been live.* `Opened` + `Status` answer the second and third, and
`age_days` is computed from `Opened` rather than stored, so the register cannot
go stale by arithmetic. Owner and mitigation should stay out: a risk with an
owner and a mitigation is *work*, and the moment you record it here you have
built the risk↔task link the rubric puts explicitly out of scope, in the weakest
possible form — a duplicate that nothing reconciles. A review date would be a
Cadence row; `## Cadence` already has a writer and a `Next due` that recomputes.
The one column I looked hard at was an explicit `Cleared` date, and it is not
needed: `risk-clear` already records `cleared_on` and the payload carries it, so
clearing does not lose the date. Four columns, and the fifth field is derived.

### Smallest change that fixes TASK-040

`risk-add` and `risk-migrate` must locate the section with the **reader's own
predicate** — the function `perry-state` calls, not a copy — and when it does not
match, **refuse**, naming the heading found and the spelling expected. Never
`ensure_section`-append a required section that may already exist under a
different spelling. Add a `perry-lint` error for two sections matching one
required heading, so this class cannot be silent again.

## 4 · TASK-044 — migration dry-runnable / lossless / recoverable / declared

Scored against **`perry/evidence/2026-08/TASK-044-spec.md`**, guarantee by
guarantee, on a copy of `~/proj/gimegime-pmo` (509 files) and a copy of
`~/proj/PolyForge`.

### Verdict: **FAIL** on one blocking finding — and **ADR-004 DOES NOT REOPEN**

Taking the second half first, because the spec says it matters more.

> **ADR-004's reopening criterion — *"migration proves unbuildable to the five
> guarantees"* — is NOT met.** Four guarantees hold outright and are asserted by
> the tool rather than asserted about. The fifth holds by design and fails only
> on `apply`'s error path, where the defect is a missing `except` and an
> ordering — not a property migration cannot have. The recovery data is already
> written before the first byte and restore already returns the tree
> byte-for-byte; nothing has to be invented to close it. **ADR-004 stands, the
> tolerance branches do not come back, and TASK-045 and TASK-047 are not
> cancelled.**

### Guarantee-by-guarantee

| # | Guarantee | Verdict |
|---|---|---|
| 1 | Dry run first, always | **PASS** |
| 2 | Nothing is lost | **PASS** — and the assertion is real, mutation-tested |
| 3 | Recoverable | **PASS** on the happy path · **FAIL** on the failure path |
| 4 | The user declares | **PASS** |
| 5 | Partial migration is a state | **PASS** by design · same failure-path gap |

**1 · Dry run first, always — PASS.**
Complete diff, not a summary and not a count: 582 lines / 29,568 bytes, longest
line 519 characters, and no `…` / `truncated` / `omitted` marker anywhere in the
output. It writes nothing — asserted by bytes, not by reading code: all 509 files
byte-identical before and after, nothing added, nothing removed. Dry run is
deterministic across two consecutive runs. And the strong form of "the dry run
and the real run produce the same result" holds: a **cold `apply` on a fresh
copy** (no dry run first) produced a tree byte-identical to dry-run-then-apply —
zero differing files. The plan promised exactly 30 files; `apply` changed exactly
those 30, with nothing promised-but-unchanged and nothing changed-but-unpromised.

**2 · Nothing is lost — PASS.** This is the one the spec says to be most
suspicious of, so I attacked it three ways.

- *Ids*: 336 → 351 by an independent regex over every `.md`. **0 lost.** The 15
  gained are the `SRC-n` provenance ids migration mints, listed individually in
  the diff.
- *Characters, independently*: for all 30 migrated files, a `SequenceMatcher`
  over the whitespace-stripped text found **0 deleted or replaced characters** —
  insertions only. The spec warns that a test migrating a Perry-generated board
  proves nothing; this ran on a year-old board nobody wrote for Perry.
- *Prose the schema cannot model*: the `## P2 (低优先 carry)` widening padded
  existing rows with empty cells and altered no cell's text. `Status: 半解` was
  **not** normalized into the enum — migration refused the file instead.
- *Mutation*: I patched `edit.after` to silently drop one `>` line per file. All
  30 files were refused (`files it would migrate: 0`), and a mutant `apply` put
  **0 bytes on disk**. The assertion is load-bearing, not decorative.

**3 · Recoverable — PASS on the happy path, FAIL on the failure path.**
It chooses a restore point over a dirty-tree refusal and *states the choice and
why* (a git-only answer excludes non-git projects; gimegime-pmo is the target).
The recovery path is shown working, not described: 31 files restored, **0 files
not byte-identical to the original**, and the only thing left behind is the run
record itself.

**The blocking finding.** When a write genuinely fails mid-`apply` — I made the
target directory read-only, which is the same shape as a full disk, a permissions
problem, or a SIGTERM — `perry-migrate` dies with an unhandled traceback:

```
Traceback (most recent call last):
  File ".../bin/perry-migrate", line 1596, in main
    applied = apply_plan(plan, schema, declare=not no_declare)
  File ".../bin/perry-migrate", line 1416, in apply_plan
    write_atomic(e.path, e.after)
PermissionError: [Errno 13] Permission denied: '.../auto_research_agent_…'
```

State left behind:

- **15 of 30 files already migrated on disk.**
- **`.perry/conformance.md` never written — 0 rows.**
- **stdout completely empty.** The restore point exists (31 entries) and works
  (I ran it: 0 files not back), but the run **never names it**.

Guarantee 3's checklist says the tool *"writes a restore point **it names in the
output**"*. On the one path where the user needs the undo command, the output is
a Python stack trace. A user who hits this sees a half-converted tree, a traceback,
and no printed way back.

**4 · The user declares — PASS.** Migration never runs as a side effect:
`perry-task list`, `perry-state`, `perry-lint`, `perry-conform status`,
`perry-explain`, `perry-diagnose`, plus writing commands `risk-add` and `intake`,
together touched only `BOARD.md`, the journal and `events.jsonl`, and created
**no** `.perry/conformance.md`. The declaration is TASK-043's marker and only
that: 30 rows written through `bin/perry-conform` with `Route: migrate`, and the
only other `.perry` file mentioning conformance is the restore JSON, which is a
byte record rather than a second declaration. The refusal matches `risk-add`'s
shape — it names the count ("3 error(s)"), names the command
(`perry-migrate apply --root …`), and points at the dry run first.

**5 · Partial migration is a state, not a failure — PASS by design.**
Per-file, and it is real. On the hardest case: `BOARD.md` is left **byte-identical**
because of `[bad-enum] Status = '半解'` — a genuine fact about the project, named
in the run — while `OKR.md` migrates and is declared. Both halves then behave:

```
PERRY_CONFORMANCE=enforce
perry-task risk-add  → refused: "BOARD.md is not Perry's shape: 3 error(s) …"
perry-conform status → OKR.md   conformant   (declared 2, route migrate)
                       BOARD.md undeclared   (3 errors)
```

"Valid" is stated, which is what the spec asks for, since it is the guarantee
with no obvious definition: *"after any run, every file is either exactly as its
author left it, or conformant."* That per-file invariant **survived my crash
test** — the victim file was byte-identical and undeclared, and no half-written
file appeared. What did not survive is the project-level record: 15 files
migrated with zero declarations is a state the tool's own § 4 says cannot exist.

### The measurement that decides whether this worked

**gimegime-pmo: 59 → 15 errors** (28 → 14 warnings), 30 files changed, 479 of 509
left byte-identical. Every one of the 15 traces to a per-file blocker the run
names individually:

| Remaining | Why, as the run states it |
|---|---|
| `BOARD.md` × 3 | blocked by `[bad-enum] Status = '半解'` — a project fact; the file is left as found |
| `phase/001…` × 2 | `[size-cap] 405 lines over the tier-1 cap of 300` |
| `phase/004…` × 3 | a KR table in the project's own vocabulary (`种子 / Owner / Deliverable`) — Perry does not recognise it and will not widen someone else's table |
| `ARCHITECTURE.md` × 1 | `[size-cap] 714 over 500` |
| `locked-design-has-plan` × 6 | cross-file findings migration **revealed** rather than created, and says so up front |

So the spec's "or" branch is satisfied. **But it should be said plainly, because
the row's `Next action` does not:** the one file that does not migrate on the
flagship project is `BOARD.md` — the file ADR-004 gates. Under TASK-047's
enforcing gate, gimegime-pmo still cannot write its board until a human edits one
Chinese status word by hand. That is consistent with guarantee 5 and it is the
headline of the migration's result on the real case.

**PolyForge: PASSES.** One sentence, exit 1, 425 bytes — no wall of output, no
half-built structure:

> `perry-migrate: refused — PolyForge has no Perry state to migrate — there is no
> BOARD.md, no OKR.md, no phase/ and no .perry/config.md.`

MINOR: PolyForge nevertheless reports 11 lint errors, all in
`.perry/diagnose/2026-08-17-diagnosis.md`, and `perry-conform status` lists that
file as `undeclared (11 lint error(s)) — 0/1 declared`. The conformance gate
points a user at `perry-migrate`; on this project that path dead-ends, because
migration's "is there anything here" test looks only for `BOARD.md`, `OKR.md`,
`phase/` and `.perry/config.md`. Two of Perry's own tools give different answers
to "does this project have Perry state".

### Smallest change that fixes TASK-044

Wrap the write loop in `apply_plan` (`bin/perry-migrate:1416`) in an `except
OSError`. On failure: stop, **roll back the files already written from the
in-memory restore point**, and exit with an ordinary `Refused` that names the
file that failed and the `perry-migrate restore <run-id>` command. If rolling
back automatically is judged too clever, the minimum is to catch, print the
restore-point id and the undo command, and declare the files that did land — so
the tree is never Perry-shaped-but-undeclared with no record that migration ran.
