# The contract-invariance gate records one branch of a union type and calls it the shape

> Found 2026-08-21 while running `tests/merge-check` before merging TASK-037
> and TASK-040. The gate was red **on the base**, so merge-check correctly
> attributed it to nobody — but the base was red because of three intake rows
> added earlier the same morning.

## What fired

```
FAIL: test_no_key_changed_type (test_contract_invariance.TestNothingIsRemovedOrRetyped)
AssertionError: ['perry-task/list: intake.oldest_undischarged was NoneType, now int'] != []
```

## Why it is not a contract violation

`schema/task-list-contract.md:301` declares the key:

```
| `oldest_undischarged` | int \| null | the `n` of the longest-waiting undischarged row |
```

**Both types are contractually correct.** Nothing about the payload changed
shape. What changed is that Perry's own `## Intake` register acquired three
undischarged rows, so the key returned the `int` half of a declared union
instead of the `null` half.

`tests/fixtures/contract-shapes.json:135` records:

```json
"intake.oldest_undischarged": "NoneType"
```

— **whichever half happened to be live on the day the baseline was captured.**

## The class

This is the defect `tests/live_state_expectations.py` (TASK-121) was built to
catch, in a form that guard does not currently cover: *a value read out of the
project it lives in, asserted equal to a literal that records what that project
happened to hold.* Here the literal is a **type**, not a count, which is why it
slipped past.

The gate's own docstring makes the claim it fails:

> *"A golden file would go stale on every legitimate addition and would be
> regenerated by whoever broke it, which is how a snapshot stops meaning
> anything. Instead this captures the payload's SHAPE."*

For a union-typed key, the recorded shape **is** a golden value, and the
predicted outcome — regenerated by whoever broke it — is exactly what the next
person will do, because the fix looks like one keystroke.

## It is five landmines, not one

Every recorded `NoneType` in the baseline is a key the contract declares as a
union, and each fires the first time the live project supplies the other half:

| path | contract | fires when |
|---|---|---|
| `perry-task/list` `intake.oldest_undischarged` | `int \| null` | **fired 2026-08-21** — any undischarged intake row |
| `perry-task/list` `risks.items[].age_days` | `int \| null` | the first risk gets an `opened` date — **which is TASK-040's subject** |
| `perry-task/list` `tasks[].created` | `string \| null` | the array's first element is a row the event log knows |
| `perry-goals/list` `krs[].current` | number or absent | the array's first KR gets a number |
| `perry-goals/list` `krs[].target` | number or absent | same |

The goals pair survived this morning's `phase/002-linkage.md` edit — which set
`P002-O1-KR1` and `P002-O1-KR2` to real numbers — only because the **first** KR in the
array still carries nulls.

## The sharper version: it is sensitive to array order

`shape()` says so in its own docstring:

> *"Lists collapse to their first element's shape: a contract promises what an
> entry looks like, not how many there are, and keying on length would make
> every board edit a contract change."*

Collapsing to element **zero** avoids keying on length and replaces it with
something narrower and less predictable: for `tasks[].created`,
`risks.items[].age_days` and `krs[].current`, the recorded type is whichever
union branch **the first array element** happened to have. Re-sorting the
array, re-prioritising a row, or closing the row that used to be first can
flip a type the contract never promised was stable — and *that* is the "every
board edit is a contract change" outcome the docstring set out to avoid.

## What a fix has to do, and what it must not

- **Must not** regenerate `contract-shapes.json` from today's live payload.
  That is the move the docstring predicts and it converts the gate into a
  snapshot test with extra steps.
- **Must** read the declared type from the contract document, so a key declared
  `int | null` accepts either branch and a key declared `int` still fails when
  it returns `null`. The contract documents are the authority; the fixture is
  a cache of one observation.
- **Must** keep the gate's real catch intact: it was proved by removing
  `tasks[].startable` and watching it go red. Any fix has to keep that mutation
  red.

  **Correction, 2026-08-28 (TASK-145).** "Both emit sites" is wrong, and it is
  wrong here and in `test_contract_invariance`'s own docstring. There are
  **three**: the two initialisers in `bin/perry-task` and the assignment at
  `bin/lib/__init__.py:824`, which puts the key back. TASK-145 proved this by
  running the *old* gate as a control against that exact mutation — the old
  gate was green on `startable` too. So the claim was wrong about the code
  before any change was made to the gate.
- For array-nested keys, collapsing to element zero should become a union over
  **every** element, or the fixture must record the union — otherwise order
  sensitivity survives the fix.

read directly:
