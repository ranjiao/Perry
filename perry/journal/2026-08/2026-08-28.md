### Dispatch attempt — TASK-203 and TASK-209 — failed before any work ran

**The cause.** `codex exec` returned a 400 on both dispatches:

> `The 'gpt-5.6-sol' model requires a newer version of Codex. Please upgrade to

`codex-cli` here is `0.139.0`. This is an environment fix — upgrade the CLI, or
point it at a model the installed version accepts — and it is the user's, not a
row on this board.

**`perry-codex-preflight` caught this, and it was overridden by a reading
error.** Run cleanly it exits **1**, refusing exactly what its docstring says it
exists to refuse: *"catches stuck CLI / broken auth / version-rejected-by-API
BEFORE we fire async dispatch."* It was invoked as
`perry-codex-preflight 2>&1 | tail -6; echo "exit=$?"`, so `$?` was **`tail`'s**
status, not the gate's — the refusal was read as a pass and the dispatch went
out anyway. The same mistake hid the failure a second time: each dispatch ran as
`codex exec … > log; echo …; tail …`, so the compound's exit status was `tail`'s
`0` while codex's own was `1`.

**The gate was not at fault and this is not another instance of the
covers-a-different-surface pattern.** It is a measurement error in how the gate
was called, and the correction is mechanical: capture the exit status of the
command being judged, never of a pipe or a chain that follows it.

One latent weakness, observed and not filed: the smoke test's token check is
`echo "$SMOKE_OUT" | grep -q "PERRY_OK"`, and `codex exec` echoes the prompt —
which contains `PERRY_OK`. Today the exit-code check fired first, so the token
check was never reached. If codex ever exits 0 while erroring, that check passes
on its own prompt.

unavailable.
