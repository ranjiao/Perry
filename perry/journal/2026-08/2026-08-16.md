## Notes

**The backward-compatibility mechanism, written down because it is easy to
break later.** `bin/perry-lint` treats every entry in a file's `headings[]` as
required, but skips a `tables[]` spec whose section is absent
(`if not bodies: continue`). So `## Tracks` in `.perry/config.md` and
`## Intake` in `BOARD.md` are declared as **table specs, never as headings** —
which is what makes them validate strictly when present and cost nothing when
absent. Moving either into `headings[]` would silently convert an opt-in into a
migration for every existing Perry project.
`tests/test_work_modes.py::TestOptInIsFree` asserts exactly that, so the trap
is now guarded rather than merely known.

Same reasoning for the two new BOARD columns: `Track` and `Verification` are
**not** in `columns[]`. The linter errors on any listed column a table lacks,
but `enum_columns` is skipped when the column index is missing — so
`Verification` is enum-checked when a board carries it and ignored when it
doesn't.

**One correction to TASK-015's spec.** The spec asked for "a `claims[]` entry
for `BOARD.md § Intake`". That was a drafting error on my part: `claims[]` is a
list of **paths**, and `BOARD.md` is already claimed. A section inside an
already-claimed file needs no new claim, and inventing a path-shaped entry for
one would have corrupted the list that DESIGN-002 exists to keep authoritative.
Implemented as an optional table spec instead, and
`test_design_003_adds_no_new_claimed_path` now asserts that none of
`INTAKE.md`, `TRACKS.md`, `packs/`, `modes/` or `sources/` ever enters
`claims[]`.

**`modes/project.md` deliberately contains no rules.** Project-mode behavior
already lives in `okr/SKILL.md` and `pmo/SKILL.md`; copying it into the mode
file would create a second authoritative copy of a rule that already has one.
So the file declares *which* existing rules constitute the mode and points at
them. The other three modes will carry real rules, because theirs exist nowhere
else yet. This is why the byte-diff no-op was achievable at all.

**A forward reference caught and removed.** The first draft of router step 3b
told the user to declare tracks with `/perry pmo track` — a subcommand that does
not exist. `reference/user-load.md` forbids referencing an ID that does not
exist yet, and a command is the same defect at the same cost. Replaced with the
truth: the register is a table in a tier-1 file the user edits directly.

## Notes

**The consequence rule found a home instead of a new field.** DESIGN-003 §5.3
says the required rung is a function of consequence, not shape — outward-facing
or irreversible work needs V5 in every mode. Nothing on a task declares that,
and adding a field would mean asking the user to classify every task twice.
`.perry/hook.md § High-stakes operations` already *is* the project's own
statement of what is dangerous, so `--verification` matches each done row
against it and reports `consequence-needs-signoff` on anything that closed
below V5. A project with an unarmed hook gets no consequence checks at all,
which is the honest behavior: nothing has told Perry what matters there.

**An empty scan is not a pass.** The first run of `--verification` on Perry's
own board printed `✓ every done row carries a satisfiable rung` — over **zero**
rows, because Perry moves closed rows out of the P-sections into `## Done this
period`. A gate that reports a checkmark for having checked nothing is how a
gate quietly stops being one, so the mode now distinguishes the three cases and
`test_an_empty_scan_is_not_a_pass` holds the line.

**`Verification` is resolved by header name, not by column position.**
`viewer/parsers.py` reads board rows positionally, which is fine for the six
columns every board has had since the beginning. An *optional* column cannot be
read that way — a board with any other extra column would rate the wrong cell.
The parser now captures the header row before the `|---` separator and looks
the column up by name, through the same i18n glossary as everything else.
`test_rung_is_resolved_by_header_name_not_position` pins it.

**`unrated` is reported separately from V1, deliberately.** "Nobody said" and
"someone said an artifact exists" are different claims, and folding the first
into the second would flatter the board during exactly the release where the
number is meant to be watched. Decision 4 made the rung advisory for one cycle
so `unrated` can shrink on its own before the gate hardens.

**Dogfood.** Perry's own board now carries the `Verification` column with each
open row's *target* rung, taken from its spec rather than invented at close
time. That is the first real board to use the optional column, and it lints
clean — which is the only proof that "optional when absent, strict when
present" actually holds outside a fixture.

edits beyond path references, that's the 'packs are wrong' finding"*. They
needed **zero** edits — not even path rewrites, because none of the three ever
referenced the others by relative path. `architecture.md`, `runbooks.md` and
`incidents.md` were already self-contained; nothing but the PMO lane index was
holding them in core. The abstraction holds, and TASK-025 (loader + glossary)
is worth building.

**Two things the extraction surfaced that the design did not anticipate.**

1. **`git-boundaries.md` is not software-ops.** The task named four files;
   three moved. That file declares which *role* may commit, push, open a PR and
   merge — and none of it is about software. A research vault, a content
   pipeline or an ops repo kept in git needs the same role boundaries, and a
   knowledge base with two sessions writing to it needs them more. Moving it
   would have made git etiquette conditional on a software pack being
   installed. It stays in `pmo/reference/`.

2. **The goals lane was carrying a hard software gate.**
   `okr/reference/phases.md` refused to write a phase file until every
   unresolved architecture-audit drift item had a response — an unconditional
   refusal keyed on `ARCHITECTURE.md`, a file only software projects have. A
   content pipeline or a research vault could never trip it; it simply sat in
   the goals lane as software's assumptions wearing the goals lane's clothes.
   Now conditional on the pack, unchanged where it applies. **This is precisely
   the class of leak DESIGN-003 § 1.4 B8 predicted, found one lane over from
   where the design expected it.**

**The rung was lowered from V4 to V3, deliberately.** TASK-024's spec said V4 —
a fresh-context reviewer scoring the extraction against a rubric. But V4 exists
to grade *authored content*, and this turned out to be a **move**: the artifact
is byte-identical to what already existed and passed review when it was
written. There is nothing for a rubric reviewer to score. The mechanical
evidence — a zero-line diff — is stronger than a judgment call, which is the
definition of V3 beating V4 for this artifact. Recorded rather than silently
downgraded, because a rung that drifts down without a reason is how a ladder
stops meaning anything.

**One authored artifact remains unreviewed**: `packs/software-ops/pack.md` is
new prose, not a move, and nothing has graded it.
