# Pipeline work

A pipeline tracks work through useful stages toward a promised outcome. Its
stages and commitments are skill conventions unless the applied native template
explicitly declares them. Inspect `template show`; do not reintroduce legacy
stage/order/commitment fields or a mode-specific JSONL register.

Agree the outcome, named owner, entry/exit criteria, consequence of failure,
capacity and review interval with the project. A promise to another party is a
goals-owned narrative; it does not make work its writer. Represent executable
work as native tasks and explicit dependencies. Record the pipeline position in
the agreed narrative when the template cannot represent it; do not claim a
computed WIP/SLA output that no current helper supplies.

At a review, page through relevant tasks and events, count the exact selected
set and state exclusions. Distinguish active work, blocked work and dropped work;
event times establish state changes, not continuous elapsed effort. Ask the owner
about stalled work before proposing reset/drop. Capacity warnings guide a choice,
never silently drop work or erase history.

Closure requires exit criteria and evidence against the promised outcome.
High-stakes consequences, V4 independence and V5 human signoff remain binding via
`reference/operating-rules.md`. A dropped task has an authorized reason; it is not
a successful delivery. The old stage/mode/verification scanners are proposed
retirements pending final H acceptance. Read actual documents and evidence in the
review rather than reporting absent automated scores as green.
