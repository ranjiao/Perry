# 三层架构分析：第一阶段计划

状态：第一阶段已实现，验证记录见 `VALIDATION.md`；目标架构与自动修复不在本次修改内。
依据：main `db06e70c`；分析原型分支 `codex/architecture-browser` 的 `fbdea556`，尚未合入。

## 三层设计

| 层 | 输入 → 输出 | 边界 |
|---|---|---|
| 1. 静态事实 | 源码 → 文件、符号、依赖、入口、源码位置与快照 | Python stdlib 实现；不执行目标代码，不判断业务含义 |
| 2. 语义现状 | 事实及相关源码 → 职责组件、层次、关系解释 | 由当前宿主 agent 生成；每个判断关联证据，未知与职责混杂必须保留 |
| 3. 目标与对比 | 用户目标 + 现状 → 偏离、证据、处理建议 | 目标由用户控制；明确规则程序检查，语义冲突交 agent 判断，不能擅改目标 |

目标架构继续以项目 `ARCHITECTURE.md` 及其引用的模块设计为权威。
程序可检查的规则从目标派生，附原文位置和版本；它们不是另一份可独立修改的目标。
现状分析先独立生成，再映射目标组件，避免把目标直接复制成“已实现架构”。

## 现有代码如何处理

| 现有部分 | 处理 |
|---|---|
| `scan.py`、`bin/perry-architecture` | 复用扫描、import 解析、无后缀 Python 脚本支持、哈希和覆盖报告；补函数/类、声明范围、可解析的直接调用和字面量入口信息 |
| `report.py`、`report.js/html/css` | 复用图、下钻、源码证据、JSON/Mermaid 导出；增加目标/现状区别与偏离面板 |
| `model.py` | 保留校验、归属覆盖检查和依赖聚合；重做输入契约，支持符号成员、证据及快照绑定，不再仅靠路径匹配 |
| `perry-model.json` | 降为旧原型样例；正式分析不依赖手写职责配置 |
| `packs/software-ops/architecture.md`、`work/reference/review.md` | 复用已有审计和架构变更决策流程；新分析结果作为审计证据，不另建治理系统 |

Perry 特例：`bin/perry` 动态加载命令，`perry-kernel-migrate` 通过子进程调用内核。
import 图不能表示这些关系；第一阶段采集可静态确定的调用/入口证据，其余标为未知。
`SURFACE` 的可静态读取字段可帮助理解命令；不能调用现有动态加载器去执行待分析项目。
Skill、schema、模板不是 Python 代码：记录覆盖边界，agent 可引用相关原文，但不能冒充静态提取结果。

## 第一阶段顺序与验收

1. **补事实。** 给现有扫描器增加符号及有限调用提取；用 Perry 的命令入口和内核验证。每条关系有类型、来源和位置；无法解析不猜测。
2. **生成现状。** 程序按结构组织证据包，宿主 agent 分批识别职责并汇总层次；输出机器可校验的现状 JSON。不给 `perry-model.json`，也能生成总览、组件和成员；不预设固定组数。
3. **对比目标。** 先验证两条现有内核规则：“不得依赖 bin/viewer/release”“不得运行命令”。报告区分确定违反、疑似偏离、无法判断；每项指向目标条款和源码。局部检查通过不等于整个架构合规。
4. **验证更新。** 每次全量重扫事实，按证据指纹使旧解释失效；比较前后组件和依赖。用隔离副本新增违规 import、命令调用及新文件，确认能发现变化；移除后重新验证。
5. **验证可迁移。** 在另一个 Python 项目上，不提供专属职责配置，重复生成现状；人工检查层次是否解释代码，而不是给目录改名。没有目标时只输出现状，不宣布合规。

输出：一份现状图、一份简短偏离清单、一份可供 agent 使用且带证据的 JSON。
人工验收关注“能否理解组件职责、追查依据、看懂变化”，不以测试通过替代架构可读性验收。

## 本阶段边界

只分析、对比和提出建议；不自动修代码、不修改目标、不启动定时任务。
已接任务开始/交付前检查：宿主流程触发、程序保留基线与对比；定期调度与自动修复留到后续。
Perry 当前 §1 限制无人值守运行；后续调度/修复需明确执行授权及适用范围。
不引入模型服务或第三方依赖，不做通用全语言分析器或完整运行时调用图。
